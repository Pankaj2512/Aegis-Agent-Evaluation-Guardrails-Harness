# Aegis — Deep Backend + Frontend Audit (2026-08-07)

One comprehensive static (code-level) audit pass. Method: 15 parallel finder agents, each owning one dimension of the codebase; findings deduplicated, then **every P0–P2 claim handed to an independent adversarial verifier** instructed to refute it by tracing the failure end-to-end (several ran targeted `pytest` repros on isolated DBs). Only findings that survived verification appear as defects. I then independently re-traced the four highest-blast-radius P1s (alert-webhook crash, `eval_trend` staleness, boolean-default migration, `/v1` viewer bypass) against source — all four confirmed.

**Baseline is green:** backend `pytest` = 361 passed / 2 skipped; frontend `tsc --noEmit` clean. Everything below is a latent defect on a healthy tree, not a broken build.

**Documented/roadmap items excluded by design** (not re-reported): Gemini-only models, no MCP client/server, worker-mode SSE/approve in-memory constraint, no durable execution, webhook-only alert channels, no CSV dataset import, no RBAC/workspaces. See `scratchpad/known_issues.md` / `docs/ROADMAP.md`.

## The eight to fix first

1. **Alert webhooks are 100% broken** — every fired alert raises `RuntimeError` instead of delivering (P1-12). Webhook is the only alert channel, so alerting silently does nothing *and* aborts the rest of that scheduler tick (retention included).
2. **Fresh-Postgres provisioning fails** — migration 002/009 emit `BOOLEAN DEFAULT 1`, which Postgres rejects; `alembic upgrade head` aborts and the strict startup gate then refuses to boot (P1-9). Invisible because CI only migrates SQLite.
3. **Viewer API keys can execute workflows and ingest data** — the read-only middleware guards `/api/` only; `/v1/invoke` and `/v1/ingest` sit outside it (P1-6).
4. **Canvas save can silently lose or clobber work** — saves never update the query cache, so back-navigation reseeds a pre-save graph and the next save overwrites the newer version in place (P1-22); `Cmd+S` also skips uncommitted textarea drafts (P1-20).
5. **Published production graph is mutable by an ordinary Save** — default save overwrites the published version in place, so `/v1/invoke` starts running half-edited drafts with no publish action (P1-8).
6. **All timestamps are wrong under SQLite** — offsetless UTC strings are parsed as local time, shifting every "x ago" and tooltip by the viewer's offset (P1-24).
7. **A Code node with an infinite loop leaks a sandbox thread permanently**; eight exhaust the process-wide pool for all users (P1-5).
8. **Cross-tenant leak in "all workflows" alert rules** — the metric is computed over every user's runs, exposing another tenant's spend/activity (P1-10).

## P1 defects (24)

### Runtime & execution correctness

**P1-1 · Run-from-here feeds the wrong value in its default modes** — `backend/app/services/context_wrapper.py:115`
`seed_pinned_outputs()` seeds the pinned predecessor into context `last_output`, but the pruned graph rewires trigger→start-node and the wrapped trigger passthrough overwrites `context_ref['last_output']` with the raw run input before the start node runs; the start node also gets the raw input positionally. *Scenario:* pin node A's output, run-from-here at B whose template is the default `{{last_output}}` (or B is an agent/tool consuming node input) → B processes the original run input, not the pinned value the feature promises. Only explicit `{{steps.<id>.output}}` templates survive — which is exactly the one case the existing test covers, masking the bug. *Fix:* have the trigger passthrough emit the seeded `last_output`, or rewire the pruned trigger to the pinned value; add an executor-level test that runs the pruned graph.

**P1-2 · Google-search tool node + error branch silently kills the pipeline** — `backend/app/services/compiler.py:588`
A `toolType=search`/`searchProvider=google` node compiles to a bare ADK `Agent` (never wrapped by `wrap_with_context`), yet validation allows error edges from any `tool` node and `_build_graph_edges` stamps its success edge `__ok__`. The bare Agent never sets `ctx.route`, so neither the success nor error edge fires and everything downstream never runs — the run "completes" with the raw search output as final output. `retries`/`timeoutSec` are also silently ignored for this variant. The same bare-Agent class was already deliberately guarded for agent/summarizer/translator/extractor/evaluation — this variant was missed. *Fix:* make `_validate_error_edges` config-aware (reject error edges from search/google tool nodes, mirror in `supportsErrorBranch`), or wrap Agent nodes with an error-intercepting adapter.

**P1-3 · Worker mode never reconciles crashed-worker runs** `[worker]` — `backend/worker.py:21`
`startup.recover_stale_runs()` no-ops in worker mode ("the worker owns recovery"), but `worker.py`'s lifespan never calls it (or `run_startup_tasks`) at all, and `sweep_stale_runs` also returns 0 in worker mode. A run orphaned in `running`/`awaiting_approval` by a worker crash is never moved to a terminal state (the claim query only picks `pending`/`queued`), so it sits `running` forever, polluting dashboards and the DB-side concurrency count. This is *not* the documented no-resume constraint — the run is never even marked failed. *Fix:* in `worker.py` lifespan, call the unguarded `recover_stale_runs` before `start_run_worker`, or add a heartbeat column the API sweep can use.

**P1-4 · Stale-run sweep fails runs resumed after a long approval pause** — `backend/app/services/run_concurrency.py:80`
`sweep_stale_runs` (every scheduler tick) reaps any `running` row with `created_at` older than `run_stale_after_seconds` (default 900s). But approval pauses are intentionally allowed to exceed the run budget (`approval_timeout_seconds` default 3600), and `approve_run` flips status back to `running`. *Scenario:* run parks at an approval node, reviewer approves at T+20min → the row is now `running` and older than the 900s cutoff → next tick sets it `failed` ("Run interrupted by server restart or crash") *while its task is actively executing*; when the task finishes, `_complete_run` overwrites back to `completed` — status thrashes `failed`→`completed`. *Fix:* in inline mode skip runs present in `executor._active_tasks`, or track last-activity/heartbeat instead of `created_at`.

**P1-5 · Infinite-loop Code node leaks a sandbox worker thread permanently** — `backend/app/services/code_sandbox.py:128`
`run_sandboxed_code` submits user code to a shared module-level `ThreadPoolExecutor(max=8)` and enforces the 5s cap only via `future.result(timeout=…)`; `future.cancel()` cannot stop a started thread, so `while True: pass` leaks that worker forever. Eight such runs exhaust the pool and every subsequent Code node — for **all users** — times out until process restart. *Fix:* run sandboxed code in a hard-killable subprocess/process-pool, or a `sys.settrace` watchdog; at minimum cap concurrent submissions and reject when no idle worker exists.

### Security & multi-tenancy

**P1-6 · Viewer read-only enforcement bypassed on `/v1` routes** — `backend/app/main.py:98` · *security*
`viewer_role_middleware` blocks mutating methods only on paths starting `/api/`, but `platform.py` mounts `POST /v1/workflows/{id}/invoke` and `POST /v1/ingest/runs` outside that prefix and neither checks role. A `viewer` key can start real Gemini-backed runs (spending budget) and create workflows/runs — confirmed with TestClient (`POST /v1/ingest/runs` → 201) while the same key correctly gets 403 on `POST /api/workflows`. *Fix:* extend the predicate to `("/api/", "/v1/")`, or better, replace the path-prefix middleware with a `require_editor` router dependency so new routers can't escape the guard.

**P1-7 · `/v1/invoke` bypasses the concurrency gate and graph/key preflight** — `backend/app/api/platform.py:214` · *consistency*
`invoke_workflow` calls `schedule_run()` without the `max_concurrent_runs` check that `POST /api/runs` and `/trigger` both enforce; `schedule_run` just does `asyncio.create_task` with no cap. A burst of `/v1/invoke` (auth disabled by default, or under the 60/min tier) runs all of them concurrently even though the cap is 5 — exhausting memory/Gemini quota — while the same burst on `/api/runs` would 429 after 5. Invoke also skips `validate_workflow_graph` and the `GOOGLE_API_KEY` preflight. *Fix:* apply the same active-run gate and preflights in `invoke_workflow`, or centralize the gate inside `schedule_run`.

**P1-8 · Default Save mutates the published version in place** — `backend/app/api/workflows.py:515` · *consistency*
`save_version` with `save_as_new_version=false` (the schema default *and* the canvas Save default) overwrites `latest.graph_json` in place with no check against `workflow.published_version_id`. *Scenario:* publish version 3 (the latest), keep editing, hit Save → version 3's graph is replaced and the next `/v1/invoke` runs the half-edited draft in production, defeating the pin publish is supposed to provide. `import_into_workflow` shares the path. *Fix:* when the in-place target equals `published_version_id`, auto-fork a new version or reject with 409.

**P1-10 · "All-workflows" alert rules leak cross-tenant metrics** — `backend/app/services/alerts.py:58` · *security*
`_metric_over_window` filters by workflow only when `rule.workflow_id` is set; for a `workflow_id=NULL` rule the metric (failure_rate, cost_usd, eval_avg, latency p95/p99, guardrail_blocks) is computed over **every user's** runs, though `AlertRule` carries `user_id` and multi-user is supported via the API-key→user map. *Scenario:* user A's all-workflows `cost_usd` rule fires on user B's spend and the AlertEvent/webhook payload exposes B's aggregate to A. *Fix:* always join `WorkflowRun→WorkflowVersion→Workflow` and filter `Workflow.user_id == rule.user_id`.

### Data & persistence

**P1-9 · Integer defaults on BOOLEAN columns break fresh-Postgres migration** — `backend/alembic/versions/002_release_25_auth_observability.py:64`
`workflow_schedules.enabled/cron_valid` (002) and `alert_rules.enabled` (009) declare `server_default=sa.text("1"/"0")` → `BOOLEAN DEFAULT 1` on Postgres, which rejects integer defaults on boolean columns (error 42804). `alembic upgrade head` on a fresh Postgres DB aborts at 002, and the strict startup gate then refuses to boot. Latent because existing PG DBs were bootstrapped via the old `create_all`+stamp path and CI runs the chain only on SQLite. *Fix:* edit 002/009 to `sa.true()`/`sa.false()` (SQLite accepts both); add a CI job that runs the chain against a real Postgres service container.

**P1-11 · `list_runs` applies the tag filter after LIMIT/OFFSET** — `backend/app/api/runs.py:90`
`GET /api/runs` fetches `order_by(created_at desc).offset().limit()` then filters the already-paginated page in Python (`if tag in (r.tags_json or [])`). Matches outside the fetched page are dropped and offset paging over the filtered set is meaningless. The frontend sends this param from the runs UI. *Scenario:* 60 recent untagged runs + older `env:prod`-tagged runs, filter `tag=env:prod`, default limit 50 → empty list even though tagged runs exist. *Fix:* push the tag predicate into SQL before pagination (JSON containment on PG, `json_each` on SQLite).

### Observability math

**P1-12 · Alert webhooks always crash (create_task from a worker thread)** — `backend/app/services/alerts.py:193` · *concurrency*
`evaluate_alert_rules()` → `schedule_task(dispatch_webhook(...))` → `asyncio.create_task()`, but its only caller is `await asyncio.to_thread(_evaluate_alerts)` (`schedule_worker.py:229`), so `create_task` runs in a thread with **no running loop** and raises `RuntimeError`. Webhook is the only alert channel → alert delivery is 100% broken; the raise also aborts evaluation of remaining rules and skips retention that tick. Verified by tracing the full call chain. *Fix:* return fired payloads and schedule webhooks on the loop, or use `run_coroutine_threadsafe`, or have `schedule_task` fall back to it when `get_running_loop()` fails.

**P1-13 · `eval_trend` returns the oldest 20 evals, not the newest** — `backend/app/services/quality_metrics.py:124`
Runs arrive `created_at DESC` (verified at `observability_service.py:49`), so `eval_trend` is newest-first; `list(reversed(eval_trend[-20:]))` slices the **last 20 = the 20 oldest** evaluated runs. *Effect:* the sparkline shows data up to ~30 runs stale, and `aggregate_workflow_quality` feeds this slice to `detect_eval_regression` whose "latest" run is really the 31st-newest — a regression in today's runs isn't flagged and an old resolved one keeps showing. `build_trust` uses the correct idiom (`list(reversed(...))[-30:]`) two functions away. *Fix:* `list(reversed(eval_trend))[-20:]` (or `eval_trend[:20]` then reverse).

### Frontend — save, cache, and leaks

**P1-19 · "Test node" runs the last-saved config, ignoring unsaved edits** `[recent]` — `frontend/src/components/canvas/inspector/NodeDataSection.tsx:220`
The step-run sends only `{node_id, input_text, extra_context}`; the backend resolves the node from the latest *persisted* version, so unsaved inspector edits are ignored and unsaved new nodes 404. *Scenario:* edit a transform template and click "Run test" without saving → the old template runs but the inline result reads as if it tested the on-screen edit. *Fix:* carry the node's current data in `NodeTestRequest` and prefer it; short of a wire change, detect dirty state and show "Testing last-saved config — save to test your edits".

**P1-20 · `Cmd+S` saves without committing DraftTextarea drafts** `[recent]` — `frontend/src/components/canvas/NodeInspector.tsx:331`
`DraftTextarea` commits only on blur, but the global `Cmd+S` handler saves immediately without blurring, so edits typed into set-fields / kb-retrieve documents / guardrail blocked-patterns are absent from the saved version while a success toast shows. Close the tab from within the field and the edit is lost entirely. *Fix:* flush pending drafts before saving — `blur()` the active element and save next tick, or have `DraftTextarea` register its draft in a ref `handleSave` commits first.

**P1-21 · SSE proxy routes never abort upstream on client disconnect** — `frontend/src/app/api/observability/stream/route.ts:12` · *resource leak*
Both SSE proxy handlers `fetch(...)` without forwarding `request.signal`; Next 14 doesn't cancel the piped upstream body when the browser disconnects. The backend observability stream is an infinite generator, so **every** `/observability` visit leaks one immortal Next→FastAPI connection plus a broker subscriber queue. The run-stream proxy has the identical defect (bounded only by run end). *Fix:* pass `signal: request.signal` in both handlers so upstream aborts and the broker unsubscribes in its `finally`.

**P1-22 · Canvas save never updates the cached workflow → lost/clobbered edits** — `frontend/src/components/canvas/WorkflowCanvas.tsx:1666` · *stale cache*
`handleSave` and run-autosave call `api.saveVersion` directly and never touch the query cache (the component imports no `queryClient`). The page seeds the canvas from `queryKeys.workflow(id)` cache at mount only, keyed by `workflow.id` (not version). *Scenario:* edit → Save → navigate away → back: cached data renders instantly and the canvas reseeds the **pre-save** graph and versionId — edits look lost. Edit+save from that stale seed and the backend writes it over the true latest version in place (P1-8), destroying the earlier save; publishing from the header would publish the stale versionId. *Fix:* after `saveVersion` (both call sites) `queryClient.setQueryData(queryKeys.workflow(id), …)` with the new latest version (or invalidate it).

### Frontend — correctness

**P1-18 · `onReconnect` lacks the group-endpoint guard** `[recent]` — `frontend/src/components/canvas/WorkflowCanvas.tsx:2443`
`onConnect` refuses group endpoints; `onReconnect` has no equivalent check, and a collapsed group presents real Handles plus re-pointed boundary edges, so dragging an edge end onto the frame writes the group id into real edge state. *Scenario:* collapse a group with boundary edge `m→B`, drag B's end to C → the real `m→B` edge becomes `source=<group id>`. On save, backend validation filters group-annotation edges, so `m` has outdegree 0 and save fails with the baffling "Workflow must end at exactly one End node…". After expanding, the corrupt edge can't render — an invisible, un-deletable edge. *Fix:* mirror `onConnect`'s guard in `onReconnect` and resolve the authoritative edge from `edgesRef.current` by `oldEdge.id` before calling `reconnectEdge`.

**P1-23 · Trust tab counts scored-but-unjudged eval runs as failures** `[recent]` — `frontend/src/components/observability/TrustDashboard.tsx:177`
The Quality pillar renders fails as `eval_evaluated - eval_passed`, but the trust endpoint counts every run with an `eval_aggregate` in `eval_evaluated` while `eval_passed` counts only `eval_passed is True`. Runs scored without a threshold (`eval_passed = null`) display as "fail" and the headline shows a destructive-red **0% pass rate** — directly contradicting the Triage tab and Home strip, which render the same data as "— · N scored · no pass/fail thresholds set". *Fix:* backend `build_trust` should add `eval_failed` (runs with `eval_passed is False`) and make `eval_pass_rate = passed/(passed+failed)`, null when no verdicts; frontend renders that and the existing "no thresholds set" copy.

**P1-24 · All timestamps mis-parsed under the default SQLite backend** — `frontend/src/lib/format-date.ts:2` · *date handling*
Every formatter does `new Date(iso)` assuming a timezone, but under SQLite (the documented dev default) `DateTime(timezone=True)` columns return **naive** UTC that FastAPI serializes without an offset (`2026-08-06T20:48:47`), and ECMA-262 parses offsetless date-times as **local** time — shifting every relative time and tooltip by the viewer's UTC offset. Postgres (aware isoformat with `+00:00`) is unaffected. *Scenario:* SQLite dev at UTC+5:30 sees a just-finished run as "5h ago" everywhere; a viewer west of UTC sees "just now" pinned for hours with future tooltips. *Fix:* a shared `parseTimestamp(iso)` that appends `Z` when no offset is present, routed through all formatters (and `lib/time-buckets.ts`); or serialize tz-aware UTC on the backend under SQLite.

### Test-coverage gaps (dark critical paths)

These are P1 because the uncovered code is core and a regression would ship green. All confirmed by inspecting the test suite.

- **P1-14 · Human-approval flow — zero integration coverage** (`backend/app/api/runs.py:576`). The handler, `awaiting_approval` transition, `/approve` approve/deny transitions, and the `HumanApprovalDenied` metrics rewrite are untested; only the low-level `wait_for_approval`/`submit_approval` primitives are unit-tested. A run-id key mismatch or a wrong status guard would strand every approval run forever with green CI.
- **P1-15 · Guardrail-block and inline eval-threshold-block failure paths — untested** (`backend/app/services/executor.py:897`). No test that executes a compiled workflow contains a guardrail or evaluation node, so the `except GuardrailBlockedError`/`EvalThresholdBlockedError` bookkeeping (failed NodeResult, `status='failed'`, metrics, quality webhook) never runs under test.
- **P1-16 · Deferred eval — the *default* eval mode — has zero executor coverage** (`backend/app/services/executor.py:938`). `evalExecutionMode` defaults to deferred for every eval node; the entire deferred block (`run_parallel_evaluations`, `_block_deferred`, `_save_deferred`) is exercised by no test. The one related test mocks `evaluate_node_async` and asserts nothing about concurrency despite its name.
- **P1-17 · `_consume_with_timeout` (run-timeout budget with approval exemption) — untested** (`backend/app/services/executor.py:327`). An inverted status check would either never time runs out (wedging `_active_tasks` slots) or kill approval-parked runs — the exact bug the function was written to prevent — with no failing test.

## Notes on method & confidence

- **77/78 confirmation rate** is high; I treated that as a signal to re-verify, not to trust blindly. My four independent re-traces (P1-9, P1-10, P1-12, P1-13, P1-6) all held. Verifiers ran live repros for several (P1-1 and P1-2 were reproduced with executor-level scripts).
- **Severity is calibrated for this product's reality:** single-user inline dev is the common path, so worker-mode and multi-tenant defects are P1/P2 not P0 (they require `RUN_EXECUTION_MODE=worker` or `auth_enabled` + multiple keys). The frontend save/cache/timestamp bugs (P1-20/22/24) hit *every* user and are the most likely to generate "it lost my work" reports.
- **`[recent]` markers** flag defects in code merged this week (canvas tiers 1–4). That surface is where the density is — expected for the newest, AI-authored code, and the reason it got the harshest finder pass.
- This was a **static pass**. Dynamic confirmation of specific findings (e.g. reproducing the SQLite timestamp shift in the running UI, or the SSE connection leak under load) is a sensible follow-up if you want any of these promoted from "traced" to "reproduced in the running app".
